\subsection*{Why cached input reached about 99 million}
At this snapshot, 97.35 million of 99.37 million logged input tokens are marked cached (97.96\%). This is cumulative input across 28 turns and 710 model calls, not one prompt and not 97 million newly written words. The conversation repeatedly carried large shared context, tool results and prior history. When a reusable prompt prefix is recognized, its tokens are still counted in total input and separately labeled as cached; cached tokens would receive a lower API rate in this hypothetical API-price comparison. Thus the cumulative cache count can become very large even if the actual new text per call is much smaller. The Codex usage records explicitly mark these tokens as cached input. OpenAI describes prompt caching as reusing saved computation state for an exact matching prompt prefix; the cached prefix still belongs to the logical conversation context. The rollout has no separate cache-diagnostics records, so I can confirm cache use from the counters but cannot identify exactly which messages made up every matched prefix. See the official \href{https://developers.openai.com/api/docs/guides/prompt-caching}{prompt-caching guide}. Across those 710 calls, all 53 Astra requests and 655 of 657 Luna requests reported some cached input; two Luna calls reported zero cached input. The largest single request had 245,235 input tokens, of which 243,328 were cached. No cache-write tokens were reported. The rollout reports a 258,400-token context window: 156 Luna calls exceeded 200,000 input tokens, 27 exceeded 230,000, and the maximum 245,235 used about 95\% of that window. This makes the \emph{per-request context size} a plausible quality risk: old material may crowd out fresh evidence or make relevant details harder to prioritize. The aggregate cache count itself is not a memory overflow, and the logs do not show that any particular answer failed because of context pressure. Exact per-message content attribution and subscription cost are not exposed.
